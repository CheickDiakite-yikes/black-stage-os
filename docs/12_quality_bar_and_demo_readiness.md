# 12 Quality Bar and Demo Readiness

## Quality thesis

Blackstage must feel like a category shift. A functional prototype that feels like a generic chatbot fails the mission.

## Product quality bar

### The stage

- Calm black field.
- Minimal default UI.
- Objects emerge from intent.
- The stage has depth and presence.
- No clutter.
- No generic SaaS dashboard feel.

### Interaction

- User intent is captured clearly.
- System response feels immediate.
- Rendered workspace matches the task.
- The user can inspect, interrupt, and approve.
- The system feels conversational without being trapped in chat.

### Agent visibility

- Agent steps are meaningful.
- Progress is understandable.
- Evidence can be expanded.
- Blockers and approvals are clear.
- No hidden "magic" for risky actions.

### Artifacts

- Outputs are usable.
- Artifacts have titles, status, and provenance.
- Artifacts can be revised.
- The user can distinguish draft vs approved.

### Research

- Key events are logged.
- Build decisions are recorded.
- Codex performance is tracked.
- Product sessions can be studied.

## The "I saw the future" test

A demo passes when a viewer can say:

1. "This is not a chatbot."
2. "I understand how I would use this."
3. "I can see what the agent is doing."
4. "I trust that I remain in control."
5. "I want to try it with my own work."

## Demo readiness checklist

- Idle state is beautiful.
- First intent submission is smooth.
- Render objects appear with purpose.
- Agent activity feed is visible.
- Approval ritual is clear.
- Artifact output is useful.
- No obvious bugs.
- No broken layout on common screen sizes.
- Demo scenario takes less than five minutes.
- Research event log captures the session.

## Visual red flags

- Chat bubble dominance.
- Traditional sidebar-heavy app.
- Too many cards at once.
- Neon sci-fi overload.
- Busy dashboard metrics.
- Generic loading spinner.
- Modal spam.
- Tiny unreadable text.
- Assistant mascot.
- No emotional presence.

## Engineering quality bar

- Typecheck passes.
- Lint passes.
- Tests pass.
- No console errors during demo.
- Components are reusable.
- State is serializable.
- Events are typed.
- Fixtures are deterministic.
- Docs are updated.

## Research quality bar

- Claims must be tied to evidence.
- User reactions should be recorded with context.
- Codex task outcomes should be logged.
- Failures are valuable and should not be hidden.
- Simulations must be labeled.
- Distinguish product findings from engineering findings.

## Launch readiness levels

### Internal demo

- Works locally.
- Clear demo fixtures.
- Basic research log.
- Known rough edges acceptable.

### Private alpha

- Real conversation/artifacts.
- Basic privacy and approval controls.
- Usable by trusted users.
- Feedback capture.

### Public research demo

- Stable enough to share.
- Clear limitations.
- No unsafe claims.
- Strong demo recording.
- Research framing.

### Product beta

- Authentication.
- Durable storage.
- Privacy controls.
- Real integrations.
- Support and error handling.
- Security review.
